## Smallest proposed startup design

1. Resolve one validated build-time native origin from the existing public endpoint variable. Browser API requests continue on the serving origin. Remove runtime setters, candidates, route parameters, ServerUrlControl, authServerDraft and choose-server recovery actions. Keep diagnostics, administration and factual privacy/operator information. Landing content already lacks the alleged hosting promotion; do not invent a landing rewrite.
2. Put a single serialized prepare-configured-session operation at the existing native storage boundary, before reading usable credentials, rendering authenticated consumers, processing logout intents or enabling replay. Keep a small local-state reader for the independent namespaces; avoid a general injectable transition framework. Return ready or blocked with a reason. Keep the gate closed on failure and allow retry without resetting data.
3. Use an atomic versioned origin-and-credentials binding. A valid binding for the configured origin is reusable. A valid known legacy origin equal to the configured origin retains its session. A provably empty installation may initialize without credentials. An unknown/malformed origin, binding, identity or unreadable state is blocked; never infer ownership from a token or choose a default legacy origin.
4. A different configured origin requires inspection of all potentially affected accounts/origins before committing a signed-out binding. Pending, failed or replaying outbox rows, drafts, pending device work, revocation/logout intents, unreadable or unrecognized state block the transition. Check SQLite schema before initialization writes. Preserve Health Connect checkpoints using their actual validators; inspect Wear inbox status conservatively. No namespace is reassigned or deleted.
5. Preserve the original session/state before committing the new signed-out binding. A failed preservation or commit leaves authentication/replay blocked and originals recoverable. The durable new binding selects the active session; old global tokens must never become a fallback. Clear active credential and consent selection while retaining origin/account-scoped consent and data. Restart after interruption must either use a verified completed binding or remain blocked, never guess completion.
6. Recovery explains the blocking state and offers retry or use of the original configured build to resolve queued work. It must not offer a picker, silent queue deletion or replay against the new destination. Matching-origin startup must retain legitimate queued work and its operation IDs.

These steps are a design, not a verified implementation. Consolidating modules does not by itself reduce complexity; retain the safety cases and use production storage mocks at the existing boundary instead of duplicating an adapter contract.

## Separate session-safety decision

The native R1 reproduction showed an old provider can overwrite replacement credentials/workspace state. A pre-write epoch check alone does not cancel an already-running storage write. Preserve that regression and its original evidence. Before removing the broad implementation, the admitted implementation must demonstrate the smallest ordering/cancellation solution against the fixed-target provider lifecycle, including remount, refresh, logout and in-flight persistence. Existing token serialization and scope checks are not proof that this race is gone.

The browser queue addresses late Set-Cookie effects, which occur before JavaScript can discard a stale response. Master’s backend credential-version and issuance changes do not establish that a valid late account cookie is harmless. Retain those regressions and disposition them against actual master. For a focused removal successor, prefer only deletion of candidate/setter APIs in the browser provider, but do not implement that reduction until the reachable race has a safe disposition.

ROOT should admit one bounded client-session safety prerequisite if these reproduced races remain reachable and cannot be addressed by a small essential guard in the removal change. That prerequisite must have its own value, source/base, maintained regressions and owner; it is not an invitation to a generic auth framework. The managed-first successor may then stack on its verified head only if it actually needs that code. No dependency on release PR441/452 or issue457 is proposed. Until this decision and bounded validation are admitted, do not delete the known fixes or claim the successor is safe. This is a coordinator scope decision, not a new request for credentials or user setup.
